# 검증 기록

2026-09-15 · Windows · Node 24.21.0 · 설치된 Chrome

## 캘린더 개선 검증

- PC 달력 옆 월 일정, 날짜 선택 시 같은 영역의 날짜 일정, 모바일 달력 아래 단일 목록으로 변경했다. 날짜 경계·공연/생일 표식·범위/종류 필터를 정리하고 Luma Card·Badge·Button 기본 스타일을 유지했다.
- `npm run build` 통과. `npx playwright test -g 'calendar changes|main routes'` 4개 통과: PC·모바일 월 이동/뒤로가기, 종류 필터와 모두 끈 빈 상태, 날짜 재선택, 월 전체 복귀, 오늘, 공연 팝업, 주요 경로 넘침/런타임 오류를 확인했다. PC 날짜 셀의 공연 Badge에서 직접 팝업을 여는 동작도 확인했다.
- 1440px 라이트, 1024px 라이트, 390px 라이트·다크, 320px 다크에서 캘린더 캡처와 가로 넘침을 확인했다. 아래 이전 전체 E2E·단위 테스트 기록과 구분하며, 이번 변경에서는 관련 E2E 4개만 실행했다.
- 최신 캘린더 화면은 `screenshots/calendar-v2-*.png`에 기록한다.

## 프로필 이미지 및 Luma 검수

공통 아티스트 이미지를 14px 라운딩의 정사각형으로 변경했다. 공식 Luma 레지스트리 18종·로컬 UI 135개 대조, 필터 라운딩 복구, 앨범·공연·세트리스트 조합 수정과 검증 결과는 [luma-audit.md](luma-audit.md)에 기록한다.

## 디자인 수정 검증 (1~4번)

- 홍보용 제목·영어 소제목·반복 슬로건·장식용 날짜·가짜 계정 영역을 제거했습니다. 홈의 검색과 즐겨찾기를 한 영역에 모았습니다.
- PC 앨범/트랙 좌우 배치, 모바일 프로필 축소와 앨범 바로 아래 트랙 배치, 모바일 캘린더의 월/선택 날짜 목록 전환을 확인했습니다.
- 수정 후 빌드와 E2E 14개가 통과했습니다. 같은 날짜 재선택 처리 보완 후 캘린더 테스트 2개를 다시 실행해 통과했습니다.
- 1440px 라이트, 390px 라이트, 1440px 다크 홈, 390px 다크 날짜 목록을 캡처해 검토했습니다. 320·768·1024px에서 홈·아티스트 상세·캘린더·설정의 가로 넘침이 없었고 여러 앨범 사이 선택이 트랙 목록에 반영됨을 확인했습니다.
- 첫 화면을 기준으로 390×844 홈에 기본 즐겨찾기 6명, 아티스트 오리곡 화면에 첫 트랙, 캘린더에 첫 월 일정이 보입니다. 고정 독 아래까지 이어지는 콘텐츠는 스크롤로 확인합니다.
- 다음 달 날짜 선택과 다른 달에서 '오늘' 복귀도 확인했습니다. 다크 모드의 선택 날짜가 ghost 버튼 hover 색상 때문에 어두워지는 충돌을 고쳐 선택 배경과 글자에 프리셋 primary 토큰이 유지되도록 했습니다.
- 이미지 소스와 크롭, mock API 계약은 변경하지 않았습니다. 아래 단위 테스트 8개는 초기 구현 검증 기록이며 이번 레이아웃 수정에서는 다시 실행하지 않았습니다.

## 통과한 검증

- `npm run build`: Vue TypeScript 검사와 Vite 정적 빌드 성공. 500 kB 초과 경고 없이 페이지·mock worker 코드를 분리했습니다.
- `npm test`: 8개 통과. 한국어/전각 검색, 동일 원곡의 다른 아티스트 시점, 한국 시간 날짜 경계, 연말 월 이동, 유효하지 않은 월, 온라인 공연 제외, 멤버별 생일, 윤년, 잘못된 영상 시점.
- `npm run test:e2e`: 14개 통과. 1440×1000 라이트 PC와 390×844 다크 모바일에서 각각 7개 시나리오.
- 주요 동작: 즐겨찾기 영속 저장, 아티스트 필터, 통합검색→라이브 시점, 세트리스트 클릭, 새로고침 시점 복원, 가사 언어 전환, 공연/가사 팝업 직접 접근·뒤로가기·Escape·포커스 복원, 월 이동, 일정 필터, 시스템/수동 테마.
- 오류 검증: 503, 빈 목록, 존재하지 않는 아티스트/경로, 이미지 실패의 fallback.
- 시각 검토: 홈·탐색·아티스트·캘린더·디스코그래피·가사 팝업·공연 팝업, 모바일 독, 라이트·다크. 검증한 주 경로에 가로 스크롤이나 Vue 런타임 예외가 없었습니다.

`screenshots/`의 파일은 디자인 검토 자료입니다. 긴 페이지의 전체 캡처에서 고정 하단 독과 팝업 배경은 캡처 당시의 뷰포트 높이에 놓입니다. 실제 팝업 화면은 [dialog-detail.png](screenshots/dialog-detail.png)에서 확인할 수 있습니다.

## YouTube 검증 범위

실제 YouTube IFrame API를 사용합니다. 핵심 자동 테스트에서는 작은 API 테스트 더블을 통해 `/lives/101?t=1088`가 `seekTo(1088)`을 요청하고, `踊り子`를 선택하면 `seekTo(587)` 및 URL·세트리스트 선택이 일치하는지 검증했습니다.

2026-09-16 재생 문제를 수정했습니다. 동일한 HACHI 영상을 숫자 루프백 주소 `127.0.0.1`에서 임베드하면 재생 불가였지만, `localhost`에서는 재생됨을 실제 Chrome에서 비교했습니다. Vite 개발·프리뷰 서버에 HTML 요청의 localhost 이동을 추가하고, 페이지에 `strict-origin-when-cross-origin` Referrer-Policy를 명시했습니다. YouTube 요청 헤더를 위조하거나 영상을 프록시하지 않습니다. 플레이어 준비 직후 무조건 `seekTo`를 호출하던 코드도 제거해 시작 시점은 embed `start` 파라미터를 사용하고 재생은 사용자의 버튼 클릭으로 시작합니다.

`npm run check:video`는 실제 네트워크로 HACHI #182(107), #181(108), #171(101)의 재생 버튼을 클릭하고 재생 상태 `1`, 증가하는 재생 시간과 디코딩 프레임을 확인해 통과했습니다. #171은 1,088초에서 시작했고, 세트리스트 `踊り子` 선택 후 587.79초·재생 상태 `1`을 확인했습니다. 영상·음원의 내용을 청취해 모든 곡과 대조한 검수는 아닙니다. 이전 2026-09-15의 재생 실패 기록은 이번 Chrome 검증으로 갱신하며, 앱 내 브라우저 재생 성공을 주장하지는 않습니다.

썸네일은 4:3 이미지의 intrinsic 크기가 grid 높이를 늘리던 문제를 고쳤습니다. 고정된 16:9 프레임 안에 이미지를 절대 배치하고, 고해상도 → 중간 해상도 → 기본 해상도 순으로 실패 시 전환합니다. HTTP 200인 120px 미제공 이미지도 감지합니다. 실제 세 썸네일은 모두 1280×720으로 표시됨을 확인했습니다.

이번 수정 검증: 빌드·단위 테스트 8개 통과. 검색/시점 복원·주요 경로 E2E 4개 통과, 썸네일 404·120px placeholder·전체 실패와 16:9 유지 E2E 2개 통과. MSW가 전달하는 이미지 요청을 context 단위에서 모킹하도록 테스트를 수정한 뒤 썸네일 2개를 재실행했습니다. 실제 검증 스크립트는 실패 시 오류 종료하며 단순한 메타데이터 성공을 재생 성공으로 간주하지 않습니다. 캡처는 `screenshots/hachi-live-*.png`입니다.

실패 시 오류 안내·재시도·선택 시점을 포함한 YouTube 원본 링크를 제공합니다. iframe 준비가 완료되지 않는 경우에도 무한 로딩 대신 15초 뒤 안내합니다.

직접 확인: 개발 서버 실행 후 `/lives/101?t=1088`에서 YouTube 재생 버튼을 누르고, 다른 세트리스트 곡을 선택합니다. `npm run check:video`는 실제 외부 플레이어 진단용이며 외부 네트워크·YouTube 정책에 영향을 받습니다.

## 범위

실제 백엔드와 DB를 실행하거나 연결하지 않았습니다. 기존 `web`의 시각 구현은 읽거나 재사용하지 않았습니다. 데이터는 디자인 검토용 선별 fixture이며, 기존 서비스 전체 데이터나 전체 API 호환성을 의미하지 않습니다. 외부 배포는 포함하지 않습니다.
