# 관리자 로컬 웹 개발 계획

작성: 2026-09-19. **계획 단계이며 미구현**. [DB 구조 계획](db-renewal-plan.md)과 함께 읽는다. 원본 요구사항은 로컬 db-migration/요구사항서.md, 스키마 참고 문서는 같은 폴더의 세 *_schema_spec.md다. 이 파일들은 참고 자료이며 아래 설계를 강제하는 실행 스크립트가 아니다.

## 확정된 범위와 보류 사항

- 음악 카탈로그(아티스트·곡·라이브·세트리스트·공연·앨범·가사·커버)부터 구축한다. Discord·Google 계정, 알림 이력, 기존 수집기 운영 상태는 별도 단계로 남긴다.
- 초기 반영 대상 데이터는 사용자의 검수가 전부 끝난 뒤 새 DB에 넣는다. 읽기 전용 연결 확인은 완료했으나 테이블 생성·데이터 적재·환경변수 전환은 하지 않았다.
- AI는 규격 JSON을 만드는 외부 준비 단계다. 관리자 웹 안에서 LLM을 자동 호출하거나 그 결과를 자동 승인하지 않는다.
- File Drop & Review와 완전 수동 등록을 모두 지원한다. 구축 후에도 같은 도구로 수정·신규 등록한다.
- **아티스트 통합 명부로 확정했다.** 원곡자·가창자·발매 참여자가 같은 활동 주체라면 같은 ID를 사용한다. 관리 화면은 관계에 따라 원곡자/가창자를 필터링하고 탐색 노출은 독립적으로 설정한다.

## 실행 구조

브라우저 → 로컬 관리자 API → 로컬 검수 저장소 / 새 Neon DB의 두 경로로 나눈다. 브라우저는 DB 비밀번호나 DB 연결 문자열을 받지 않는다.

| 위치(제안) | 역할 |
| --- | --- |
| admin-web/ | Vue 3 + TypeScript + Vite 관리자 전용 프론트 |
| app/admin/main.py | 별도 로컬 FastAPI 진입점. 기존 runtime·scheduler를 import/기동하지 않음 |
| app/admin/services/ | JSON 검증·차이 비교·승인·적재 서비스 |
| app/catalog/ | 새 DB 모델·조회/저장 repository. 사용자 조회 API와 관리자 서비스가 공유 |
| migrations/catalog/ | 버전 관리되는 새 스키마 마이그레이션 |
| schemas/import/v1/ | AI 출력용 JSON Schema와 비밀 없는 예제 |
| db-migration/input/ | 사람이 투입한 JSON 원본 |
| db-migration/workspace/ | 검수 SQLite, 원본 스냅샷, 임시 편집 |
| db-migration/reports/ | 오류·중복·반영 미리보기·결과 내보내기 |
| db-migration/archive/ | 반영/제외가 끝난 입력 파일의 보관 사본 |

admin-web은 web와 같은 디자인 기반을 사용하지만 별도 앱이다. 현재 web의 프록시는 GET/HEAD만 허용하므로 이 제한을 풀어 관리 기능을 섞지 않는다. 운영 배포에서 관리 router를 기본 API에 등록하지 않는다.

개발 포트는 관리자 프론트 localhost:5176, API 127.0.0.1:8010을 제안한다. 배포 빌드는 로컬 API가 정적 파일을 제공하여 한 포트로 사용할 수 있게 한다. 포트 충돌은 시작 시 명확히 안내한다. 외부 서버 배포·LAN 공개·원격 공동 편집은 1차 범위 밖이다. Neon은 원격 DB이며 “로컬 전용”은 관리 화면/API 실행 위치를 뜻한다.

DB_KEY.txt는 현재 접속 확인 자료다. 구현 시 서버 전용 설정으로 옮기고 프론트 VITE_* 값으로 넣지 않는다. 관리 API 시작에서 구형 init_db()를 호출하지 않으며 마이그레이션도 별도 명령으로 실행한다.

## 로컬 검수 저장소

JSON 파일 자체를 검수 상태의 유일한 저장소로 쓰면 수정 이력·관계·중단 복구가 어렵다. **원본 파일 + 로컬 SQLite 작업 장부**를 권장한다. SQLite는 새 서비스 DB를 대체하지 않고 이 PC의 검수 상태만 저장한다.

| 로컬 테이블 | 저장하는 것 |
| --- | --- |
| import_batches / input_files | 배치, 파일 경로/해시, 문서 버전, 읽기 결과 |
| draft_entities | 종류, client_ref, 원본/현재 payload, revision, 상태 |
| draft_relations | 초안끼리 또는 기존 DB ID와의 연결 |
| review_events | 수정·승인·반려·제외 이력, 승인한 revision/hash |
| validation_issues | 오류/경고, 해당 필드·관계·해결 상태 |
| publish_plans / publish_attempts | 고정된 반영 목록·해시, 작업 ID, 진행/결과 |
| remote_id_map | 로컬 client_ref와 새 DB ID의 확정 대응 |

검수 SQLite와 파일 스냅샷을 함께 백업/내보내기 한다. 임시 작업 장부를 지워도 원본을 추적할 수 있게 dump 해시와 원본 table/id를 기록한다. 동시에 여러 브라우저를 열 때 revision으로 덮어쓰기를 방지하고 로컬 쓰기는 짧은 트랜잭션으로 직렬화한다. SQLite는 동시에 하나의 쓰기 트랜잭션을 허용하므로 장시간 네트워크 요청을 그 안에서 기다리지 않는다. [SQLite 트랜잭션 문서](https://www.sqlite.org/lang_transaction.html)

검토 메모·AI 확신도·보류 사유는 로컬에 둔다. 새 DB에는 승인된 카탈로그와 출처·변경/반영 영수증만 저장한다. 라이브의 세트리스트 유무, 영상 공개 여부 같은 서비스 상태는 검수 상태와 별개다.

## 파일 투입과 JSON 계약

폴더 새로고침으로 파일을 발견한다. 선택적 감시는 새 파일 도착 표시까지만 하고 승인·DB 반영은 시작하지 않는다. 확장자만 믿지 않고 내용·버전·필수 필드·크기·관계 참조를 검증한다. input 바깥 경로, symlink/junction 우회, 파일에 포함된 실행 명령·SQL·외부 schema 참조는 허용하지 않는다.

제안 envelope:

~~~json
{
  "schema_version": "1",
  "batch_id": "UUID",
  "entities": [
    {
      "client_ref": "artist:hachi",
      "entity_type": "artist",
      "operation": "create",
      "data": {
        "name_native": "HACHI",
        "name_ko": null,
        "entity_kind": "solo",
        "show_in_catalog": true
      },
      "provenance": {
        "source_url": "https://example.com/official-profile",
        "legacy": {"table": "artists", "id": 2}
      }
    }
  ]
}
~~~

예제의 URL/ID는 형식 설명용이며 검수된 실제 데이터나 입력용 seed가 아니다. client_ref는 파일 내/배치 간 관계를 연결하는 임시 키이고 DB 숫자 ID와 다르다. 관계는 artist_ref/song_ref 등 타입이 정해진 필드로 전달한다. AI가 정한 숫자 DB ID를 INSERT에 그대로 사용하지 않는다.

- create와 update를 명시한다. update는 target_id + expected_version + 변경 필드만 포함한다.
- 누락 필드는 유지, 명시적 null은 비우기다. 이름/플랫폼 ID 충돌을 upsert로 자동 덮어쓰지 않는다.
- 입력에 approved/reviewed_at이 있어도 신뢰하지 않는다. 승인 기록은 웹에서 사람의 동작으로만 만든다.
- 같은 batch_id+파일 해시는 재읽기에도 같은 초안을 반환한다. 같은 batch_id 내용 변경은 충돌 또는 새 revision으로 다룬다.
- 원본 JSON은 보존하고 웹 수정은 별도 초안으로 저장한다. 편집 결과 JSON을 다시 내보낼 수 있다.
- 라이브는 방송 한 건과 전체 세트리스트를 검수 단위로 묶되 곡·가창자 참조는 독립 마스터를 가리킨다.
- 파일 크기·배치 개수에 상한을 둔다. 최초 구현에서 10MiB/파일·1,000개 최상위 항목을 출발점으로 시험하고 큰 덤프는 추출 단계에서 여러 파일로 나눈다. 파싱 제한 초과는 원본을 손상시키지 않고 오류로 보고한다.

## 검수 상태와 초기 반영 관문

상태: 발견 → 검증 오류 또는 검수 대기 → 수정 중 → 승인 / 보류 / 제외 → 반영 중 → 반영 완료. 제외에는 이유를 남긴다. 승인은 현재 revision과 payload 해시에 묶는다. 승인 후 값·관계가 바뀌면 승인을 해제한다. 연결 대상의 변경도 영향 목록에 표시하고 관련 승인을 다시 확인한다.

**검수 완료와 DB 저장은 다른 동작이다.** 초기에는 승인 버튼을 눌러도 새 DB에 카탈로그 행을 쓰지 않는다.

1. 사용자가 초기 배치를 구성한다. 포함하지 않을 자료는 명시적으로 제외한다.
2. 배치 안 모든 항목이 승인 또는 제외로 정리되어야 한다. 보류·오류·미해결 참조가 있으면 초기 반영을 막는다.
3. 승인 대상과 의존 마스터를 고정한 manifest를 만든다. 고정 후 새 입력 파일은 다음 배치이며 기존 manifest를 바꾸지 않는다.
4. 새 DB 대상, 생성/수정 건수, 제외 목록, 연결 관계와 차이를 미리 본다.
5. [초기 데이터 반영]을 누를 때 서버가 대상 DB·스키마 버전·manifest 해시·초안 revision·참조를 다시 검증한다.
6. 승인된 manifest만 한 DB 트랜잭션으로 반영한다. 현재 규모를 실제로 시험해 시간/메모리 한계를 확인한다. 실패 시 전부 rollback하며 임의로 부분 반영으로 바꾸지 않는다.
7. 반영 영수증이 확인된 뒤 초기 구축 완료 상태로 전환한다.

검수자가 곡 미매칭을 확인하고 song_id를 null로 남기는 것은 허용한다. 존재하지 않는 client_ref나 제외된 초안을 계속 참조하는 것은 미해결 참조이므로 반영을 막는다. ‘모름을 확인한 데이터’와 ‘깨진 연결’을 구별한다.

“검수를 끝낸 데이터만”은 파일을 열었다는 의미가 아니다. 화면의 변경 내용과 관계를 보고 해당 revision을 승인한 기록을 뜻한다. 대량 승인은 현재 선택된 항목·수량·요약을 명시하며 숨겨진 페이지 전체를 자동 선택하지 않는다.

## 수동 등록과 구축 후 관리

초기 구축 중 [추가]는 동일한 초기 초안에 넣는다. 초기 검수 이전 입력 금지와 수동 즉시 저장 요구가 겹치는 부분은 초기 관문을 우선한다.

구축 완료 후에는 [추가] → 입력 → [저장] 한 번으로 원격 DB에 반영한다. 사람이 폼을 작성하고 저장한 행위가 승인이다. 불필요한 별도 승인 큐는 강제하지 않는다. 연결 아티스트/곡을 같은 작업에서 만들 수 있고 전체 작업은 하나의 트랜잭션이다.

기존 자료 수정은 원격 현재값과 편집값을 비교하고 version 불일치는 409로 반환한다. 다른 작업이 바꾼 값을 조용히 덮어쓰지 않는다. 삭제 기본은 사용 중지/숨김이며, 참조가 있는 마스터의 물리 삭제는 막는다. 병합은 관계 재연결·별칭·외부 ID 충돌·출처 보존을 미리 보여주는 별도 작업으로 한다.

## 화면 구성

| 메뉴 | 주요 기능 |
| --- | --- |
| 검수함 | 배치/항목 종류/상태/경고 필터, 검색, 페이지, 진행률, 다음 미검수 이동 |
| 아티스트 | 프로필·언어·별칭·소속사·그룹/멤버·외부 계정·탐색 노출 |
| 곡 | 원곡자·작사/작곡·이름·노래방 번호, 중복 후보와 연결 기록 |
| 라이브 | 영상 메타데이터, 원문 댓글 ↔ 세트리스트, 가창자·곡·시점 편집 |
| 공연 | 날짜 정확도·시간대·다중 출연진·공연장·취소/연기·티켓 |
| 음반·가사 | 앨범·녹음/트랙·디스크 순서, 가사/번역/발음·크레딧 |
| 커버 | 영상·곡·참여자 연결, 라이브와 중복된 영상 분류 |
| 반영 이력·설정 | 대상 DB 별칭, 스키마 버전, manifest, 성공/실패·재시도, 로컬 백업 |

가장 중요한 검수 화면은 PC 3영역으로 구성한다: 왼쪽 항목 목록, 가운데 수정 폼, 오른쪽 원본/기존 DB/변경 비교. 라이브 검수는 영상+댓글과 행 편집기를 함께 보며 곡명·원곡자·가창자 선택과 시점 재생을 제공한다. API GET이 영상을 새로 수집하거나 번역하지 않는다. YouTube 임베드는 사용자가 열 때 외부 네트워크를 사용한다.

긴 목록은 서버(로컬 API) 검색·정렬·50행 페이지를 기본으로 하고 84,100개 행 전체를 브라우저에 내려보내지 않는다. 선택한 항목의 위치·필터를 유지하며 검수 후 다음 항목으로 이동한다. 진행률은 승인·제외·보류를 분리해 표시한다.

## 디자인 시스템

web/components.json과 web/src/style.css의 Luma / Neutral / Inter / Lucide를 기준으로 한다. admin-web 신규 생성 시 동일 --preset a2vfHFI를 CLI에 적용하고 실제 생성 토큰을 비교한다. 이 단계에서 사용자 웹 전체 레이아웃을 공용 패키지로 재구성하지 않는다.

Sidebar, Table, Tabs, InputGroup, Field, Select/Combobox, Badge, Pagination, Sheet/Dialog, AlertDialog, Skeleton, Empty를 조합한다. 기존 컴포넌트 유무·사용법은 구현 시 shadcn-vue 스킬로 확인한다. 색상·반경을 임의로 덮거나 별도 모달/탭 시스템을 만들지 않는다.

장시간 검수 중심의 PC 배치로 만들고 좁은 화면은 목록 → 편집 → 원본 탭으로 전환한다. 모바일에서 삭제/승인을 hover에 숨기지 않는다. 상태는 색만으로 구분하지 않고 텍스트·아이콘을 함께 쓴다. 모션은 저장 피드백·패널 전환에만 짧게 적용하고 reduced-motion을 지킨다. shadcn-vue와 transitions-dev가 겹치면 shadcn-vue를 우선한다.

## 제안 API와 실패 복구

별도 로컬 앱의 /api/admin 아래에 둔다.

| API | 역할 |
| --- | --- |
| GET /connection, /schema | 비밀 없는 대상 별칭/연결·스키마 상태 |
| POST /imports/scan | input 파일 발견·로컬 초안 생성. 원격 쓰기 없음 |
| GET /batches, /drafts | 필터·정렬·페이지 |
| GET/PATCH /drafts/{id} | 원본·현재값·오류 / revision 조건 편집 |
| POST /drafts/{id}/approve 또는 /exclude | 로컬 검수 상태 변경 |
| POST /batches/{id}/preview | 의존성·차이 검사 후 고정 manifest 생성 |
| POST /publications | manifest_id + hash + operation_id로 명시적 원격 반영 |
| GET /publications/{operation_id} | 중단 후 결과 확인 |
| GET/POST/PATCH /catalog/{resource} | 구축 후 조회·수동 등록·수정. resource allowlist |
| POST /catalog/.../merge-preview, /merge | 검토한 병합만 수행 |

입력 오류는 422, 버전/외부 ID 충돌은 409, 없는 대상은 404. 필드별 오류 위치와 해결책을 표시한다. 저장 성공 toast만 보여주지 않고 원격 ID·반영 건수·제외·실패 정보를 남긴다.

원격 트랜잭션에는 catalog_imports 영수증을 operation_id UNIQUE로 함께 기록한다. 같은 ID+같은 해시는 기존 결과를 반환하고 다른 해시는 충돌이다. 원격 COMMIT 직후 로컬 앱이 죽어도 재시작 시 영수증으로 성공을 확인한다. 시간 초과를 곧바로 실패/자동 재전송으로 단정하지 않는다. 로컬 SQLite와 Neon 사이에 하나의 원자적 트랜잭션이 있다고 가정하지 않는다.

## 로컬 접근 제어

127.0.0.1에만 바인딩하고 Host/Origin allowlist를 검사한다. 실행 세션용 로컬 인증과 CSRF 방어를 두며 CORS *는 사용하지 않는다. DB 키와 관리자 토큰을 URL query·프론트 번들·로그에 노출하지 않는다. 원문 댓글·JSON 문자열은 텍스트로 렌더링한다. 링크는 http/https allowlist를 사용한다.

이 도구는 한 PC의 운영자용이며 Discord 로그인을 필수로 만들지 않는 별도 로컬 진입점이다. 기존 공개 API의 관리 인증 규칙을 약화시키지 않는다. 원격 공동 관리가 필요해지면 별도 인증 설계가 필요하다.

## 구현 순서와 완료 기준

1. **상세 계약 확정:** 확정된 통합 명부를 기준으로 집계 기준, JSON v1, 초기 승인 관문과 테이블 관계 구체화.
2. **로컬 기반:** 별도 앱·디자인 시스템·SQLite·입력 파서·검수 상태. 새 DB 쓰기 없이 원본 보존/재시작 복구 검증.
3. **아티스트·곡:** 명부·별칭·원곡자·중복 후보·관계 선택과 수동 폼.
4. **라이브 검수:** 영상 중복 묶음·댓글 대조·세트리스트·미매칭 곡·합동 가창.
5. **공연·음반·가사·커버:** 같은 초안/승인/관계 엔진에 편집기 추가.
6. **반영 엔진:** migration으로 빈 스키마 준비, 승인 manifest만 쓰기, 원격 receipt·중복 재시도·충돌 검사. 합성 데이터로 먼저 시험.
7. **사용자 초기 검수:** 실제 덤프 후보 검수. 모든 포함 항목 검수 후 명시적 초기 반영.
8. **서비스 전환:** 조회 API/프론트 계약 적응, 검증 후 로컬 앱의 기본 DB 변경. 운영 worker는 별도 이전 전까지 새 DB에 실행하지 않음.

핵심 테스트: 미검수 초기 반영 차단, 수정 후 승인 해제, 미해결/제외된 참조 차단, 중복 파일/동시 저장, 트랜잭션 중단, COMMIT 후 응답 유실, 다른 DB로 대상 변경, 원격 버전 충돌, 잘못된 날짜/시점, 이름만 같은 다른 곡, 합동 가창 집계. 실데이터를 승인 없이 시험 INSERT하지 않는다.

완료는 “폼이 보임”이 아니라 로컬에서 검수 후 승인한 내용만 새 DB에 들어가고 재시도·중단·후속 수정을 안전하게 이어갈 수 있는 상태다.
