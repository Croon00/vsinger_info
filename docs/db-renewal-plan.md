# 새 DB 구조와 이전 계획

> 현재 구현 목표는 [백엔드 통합 최종 계획](backend-consolidation-plan.md)을 따른다. 신규 DB 하나로 운영하고 수집·알림 필수 항목만 선별 이전하며 기존 DB는 변경하지 않는다. X는 external_accounts 기반 저장·URL 알림, Google Calendar는 데이터 보존·legacy 격리, admin-web 개편은 후속 작업이다. 아래는 2026-09-19의 음악 도메인 설계·적용 기록이며 당시 환경설정·초기 데이터 상태를 현재 전환 지침으로 사용하지 않는다. 이후 반영은 [세트리스트 이관 결과](setlist-migration-report.md)를 참조한다.

작성: 2026-09-19. **2026-09-19 원격 스키마 적용 완료. 초기 음악 데이터와 기존 서비스 연결은 변경하지 않았다.** 이 문서는 도메인 설계 기준이며 실행된 DDL·검증 범위는 [마이그레이션 안내](../migrations/catalog/README.md)를 따른다. [관리자 웹 계획](admin-web-plan.md)은 이 구조의 검수·입력·유지관리 방법을 다룬다.

## 1. 범위와 결정

2026-09-19 간소화 결정: 곡의 title_latin·language_code·노래방 번호는 유지한다. 이미지 출처 별도 필드, 별도 표시 링크 표, 음악 크레딧, 곡 slug, 원곡자/공연의 세부 역할, 기존 ID 대응은 제거한다. 아티스트 slug와 실제 가창자 관계는 유지한다.

- 새 DB는 Git 제외 `.env.catalog`의 `NEW_CATALOG_DATABASE_URL`로 연결한다. 원격 DB는 이미 준비되어 있으며 신규 서버를 추가 생성할 필요는 없다.
- **아티스트 통합 명부로 확정.** 원곡자·가창자·발매 참여자를 각각 중복 등록하지 않고 같은 음악 활동 주체 ID를 관계에서 참조한다.
- **음악 카탈로그 우선 이전으로 확정.** Discord·Google 계정, 알림/동기화 이력, 수집 재시도 상태는 별도 단계다.
- 초기 입력 대상은 모두 사용자 검수 후 반영한다. 원본 덤프를 새 DB에 통째로 복원하지 않는다. 기존 ready/reviewed 플래그나 AI 확신도를 새 승인으로 인정하지 않는다.
- 관리자 검수 초안·승인 메모는 로컬에 저장한다. 원격에는 승인된 카탈로그, 출처, 저장 영수증·변경 이력을 둔다.
- 세 가지 참고 사양은 출발점으로 활용하되 데이터 누락·협업·향후 곡 중심 검색을 막는 제약은 조정한다.

확인한 실제 자료 경로는 프로젝트 루트의 db-migration이다. 요구사항서.md, artist_schema_spec.md, live_music_schema_spec.md, concert_discography_schema_spec.md와 schedule_music-backup.dump를 확인했다. 비밀번호·호스트·접속 문자열은 이 문서에 기록하지 않는다.

## 2. 현재 확인 결과

2026-09-19 새 DB에 **읽기 전용 트랜잭션**으로 사전 연결했다. PostgreSQL 18.6이며 사전 조회 당시 시스템 스키마 외 사용자 테이블은 0개였다. 이후 사용자 요청으로 카탈로그 표 31개와 마이그레이션 이력 표 1개를 생성했다. 별도 연결에서 음악 데이터 0건·초기 반영 미완료 상태를 확인했다. 기존 DATABASE_URL, 실행 서버, 수집기 설정은 변경하지 않았다.

덤프는 PostgreSQL 18.6 custom/gzip 형식, 약 12.2MB, public 테이블 20개다. pg_restore를 SQL 출력/목록 읽기 용도로만 사용했고 DB 복원은 실행하지 않았다. 카탈로그 관련 14개 테이블의 COPY 데이터를 오프라인 집계했다. 민감한 OAuth·알림 계정 행은 데이터 분석 대상에서 제외했다.

특히 라이브 6,513건에는 source_id가 없고 370건은 방송 시각이 없다. source_id 누락이 곧 가창자 미상이라는 뜻은 아니므로 performer_name·채널·댓글을 함께 검토한다. 원곡 아티스트가 없는 가창 기록은 20,950건, 한국어 곡명이 없는 기록은 16,610건이다.

117은 중복된 영상 ID의 종류 수이며 “삭제해야 할 행 수”가 아니다. 공동 진행 방송이 가창자별로 중복 저장됐을 수도 있으므로 영상 하나 아래 출연 관계를 합칠지 사람이 결정한다. 동일 archive_id+시점+곡명+원곡자의 완전 일치 중복 추가 행은 이번 집계에서 0이었으나 다른 아카이브 ID·다른 표기의 의미상 중복이 없다는 뜻은 아니다.

공연 후보 357건 전부 기존 status는 ready지만 시작 값 누락 119건, 형태 unknown 75건이다. ready를 검수 완료/공연 확정으로 해석하지 않는다. 분석 근거는 Git 제외된 db-migration/dump-inventory.json과 connection-check.json이다. 비밀값과 원문 레코드는 이 보고서에 넣지 않았다.

## 3. 이해하기 쉬운 핵심 관계

- **아티스트:** 사람/그룹의 주소록. 이름·별칭은 한 번 저장한다.
- **곡:** 「Lemon」이라는 작품 자체.
- **녹음/트랙:** 그 곡을 특정 가수가 특정 버전으로 발매한 음원.
- **라이브 가창 기록:** 특정 방송 15분 30초에 그 곡을 부른 한 번의 사건.
- **원곡자·가창자·발매 참여자:** 명부 종류가 아니라 각 관계에서의 역할.

예를 들어 HACHI 한 명이 다른 가수의 곡을 부를 때는 가창자로, 자기 오리지널 곡에서는 원곡자로 같은 ID를 사용한다. 원곡자로만 등록한 요네즈 켄시는 show_in_catalog=false로 두어 탐색 격자에서 숨길 수 있다. 곡 검색과 원곡자 통계에는 정상적으로 연결된다.

관리 화면의 “원곡자”, “가창자” 목록은 관계 존재 여부로 필터링한다. 별도 is_original_artist/is_performer 플래그를 중복 관리하지 않는다. show_in_catalog는 노출 정책이고, 외부 계정의 collection_enabled는 수집 정책이다. 서로 자동 연동하지 않는다.

관계 요약:

| 대상 | 아티스트 명부와 연결 | 다른 핵심 연결 |
| --- | --- | --- |
| 곡 songs | song_artists로 원곡자 연결 | 가창 기록·녹음·커버가 같은 곡 ID를 참조 |
| 라이브 live_archives | archive_artists로 방송 참여자 연결 | 영상 videos 한 건, 여러 가창 기록 |
| 가창 기록 performances | performance_artists로 실제 가창자 연결 | 방송 한 건과 곡 한 건(미매칭은 비움) |
| 녹음 recordings | recording_artists로 음원 가창자 연결 | 곡, 가사, album_tracks를 통한 앨범 수록 위치 |
| 앨범 albums | album_artists로 발매 명의 연결 | album_tracks로 여러 녹음 수록 |
| 공연 concerts | concert_artists로 출연진 연결 | 여러 티켓 판매 구간 |
| 커버 covers | cover_artists로 실제 참여자 연결 | 영상 한 건과 곡 한 건(미매칭은 비움) |

여러 사람과 연결하는 얇은 연결 테이블은 주체·대상·역할·표시 순서를 저장한다. 현재 관리자에서는 각 연결 자료의 폼에서 대상을 검색하여 추가한다. 부모 폼에서 여러 참여자를 한 번에 편집하는 화면은 후속 개선이다.

## 4. 공통 규칙

- 카탈로그 PK는 INTEGER GENERATED BY DEFAULT AS IDENTITY를 권장한다. 현재 규모와 프론트 숫자 ID에 충분하다. 로컬 초안/반영 작업에는 UUID를 쓰고 DB ID는 서버가 할당한다.
- 기존 숫자 ID와 새 ID를 같은 의미로 가정하지 않는다. 기존 DB와 새 ID 대응표는 만들지 않는다. 원본 덤프는 별도 백업으로 보관한다.
- created_at/updated_at은 TIMESTAMPTZ, 수정 가능한 주 엔티티에는 version INTEGER를 두어 낙관적 잠금에 사용한다. 참여자 등 종속 관계를 수정할 때도 같은 트랜잭션에서 부모 version을 올린다.
- 원어 이름/제목은 필수, name_ko/title_ko/name_latin/title_latin은 nullable. 영어 원어를 한국어 칸에 중복 저장하지 않고 화면에서 fallback한다.
- 아티스트 slug는 사람이 읽기 쉬운 URL용 고유 코드다. 이름 자동 변경 시 slug를 바꾸지 않으며 영문명을 모른다고 임의 로마자를 공식 이름으로 저장하지 않는다. 필요하면 name-숫자 같은 중립 코드를 제안해 검수한다.
- 이름과 곡명에는 UNIQUE를 걸지 않는다. 동명이인·동명곡이 존재한다. 정확한 외부 ID, 승인된 동일성 판단, 관계를 통해 연결한다.
- 검색용 키는 NFKC·대소문자·공백 정리를 적용하되 원문은 별도 보존한다. 검색 정규화 결과만으로 자동 병합하지 않는다.
- 부모 엔티티 삭제는 기본 RESTRICT다. 마스터 삭제가 가창/공연 이력을 연쇄 삭제하면 안 된다. 명시적 부모 삭제 시 그 부모 소유의 연결 행만 CASCADE한다.
- 상태는 CHECK/코드 allowlist로 제한한다. 범위 CHECK·FK·UNIQUE와 트랜잭션 서비스 검증을 병행한다.
- JSONB는 원문 근거·외부 응답 스냅샷·반영 결과/변경 이력에 사용한다. 곡/가창자/출연진 같은 핵심 관계를 JSON 배열로 저장하지 않는다.
- 스키마 변경은 Alembic 등 버전 마이그레이션으로 관리하고 구형 init_db()의 자동 ALTER/seed를 새 DB에 실행하지 않는다.

## 5. 도메인별 테이블

아래는 최소 구현을 위한 필드 중심 설계다. 공통 id/시각/version은 반복해서 적지 않았다. 모든 테이블을 같은 날 화면으로 구현할 필요는 없지만 FK 구조는 마이그레이션에서 일관되게 준비한다.

### A. 아티스트와 외부 계정

| 테이블 | 주요 필드 | 관계·규칙 |
| --- | --- | --- |
| artists | slug, name_native, name_ko?, name_latin?, entity_kind(solo/group), is_virtual?, agency_id?, birthday_month/day?, debut_date?, bio?, theme_color?, avatar_url?, show_in_catalog | 원곡자와 가창자 공통. vtuber/singer/group을 같은 분류축에 섞지 않음 |
| artist_aliases | artist_id, alias, normalized_alias | 아티스트 내 동일 별칭 중복 방지. 다른 사람의 같은 별칭은 허용 |
| agencies | name_native, name_ko?, website_url? | 소속사는 가창자가 아님. 문자열 철자 차이를 줄이는 선택 FK |
| artist_group_members | group_id, member_id, joined_on?, left_on? | 자기 자신 금지, 그룹→솔로 검증. 1차는 동일 쌍 한 행; 재가입 이력은 필요 시 확장 |
| external_accounts | platform, platform_id?, handle?, url, collection_enabled | YouTube·Spotify·공식 사이트·팬클럽 링크 통합. 외부 ID가 있으면 platform+ID UNIQUE. 기본 수집 비활성 |
| artist_external_accounts | artist_id, account_id, relationship(owner/member), is_primary, label?, position | 공유 계정 연결과 프로필 버튼의 표시 이름·순서를 함께 관리. 웹사이트는 외부 ID 없이 URL만 입력 |

name_ko/name_latin은 필수가 아니다. 솔로/그룹과 가상 캐릭터 여부는 독립적이다. 생일은 월/일을 둘 다 비우거나 함께 입력한다. 2월 30일 같은 날짜를 막고 2월 29일은 허용하며 평년에는 임의로 2월 28일 일정으로 옮기지 않는다. 그룹 창설일을 멤버 생일로 대체하지 않는다.

group_id가 실제 그룹인지와 시간 구간·반복 관계 같은 교차 행 규칙은 서비스/필요한 trigger에서 검증한다. 단순 CHECK가 다른 테이블을 조회하도록 설계하지 않는다. [PostgreSQL 제약조건](https://www.postgresql.org/docs/18/ddl-constraints.html)

### B. 곡과 원곡 아티스트

| 테이블 | 주요 필드 | 관계·규칙 |
| --- | --- | --- |
| songs | title_native, title_ko?, title_latin?, language_code? | 작품 마스터. Spotify 한 트랙과 동일시하지 않음 |
| song_artists | song_id, artist_id, position | 여러 원곡 명의 허용. 역할 구분 없이 같은 곡·아티스트 중복 금지 |
| karaoke_numbers | song_id, provider(tj/ky), number, source_url? | 곡별 복수 번호 허용. 검수된 번호만 입력 |

원곡 아티스트는 화면에 표시하고 검색·집계할 공식 명의로 검수한다. 보컬로이드 P·가창 캐릭터를 의무적으로 모두 등록하지 않으며 원곡 가창/제작 역할을 나누지 않는다. 작사·작곡·편곡·프로듀싱 크레딧은 수집·저장 범위에서 제외한다. song_artists가 비어 있는 검수된 곡도 저장 가능하되 원곡자 미확정으로 표시한다.

곡 검색 별칭 테이블은 1차에 추가하지 않는다. 원어/한국어/영문 필드로 검색하고 과거 잘못된 제목은 원문/검수 장부에 보존한다. 유용한 곡 약칭 요구가 생기면 song_aliases를 확장한다.

### C. 영상·라이브·가창

| 테이블 | 주요 필드 | 관계·규칙 |
| --- | --- | --- |
| videos | platform, platform_video_id, source_account_id?, title, published_at?, duration_seconds?, availability | YouTube ID 11자리 검증, platform+ID UNIQUE. URL은 ID로 생성 가능 |
| live_archives | video_id UNIQUE, primary_artist_id?, broadcast_at?, setlist_state(unprocessed/partial/complete/unavailable) | 진행자/채널과 실제 가창자를 구분. 타이틀·길이를 영상과 중복 저장하지 않음 |
| archive_artists | archive_id, artist_id, role(host/guest), position | 방송 참여자. 모르는 관계는 생성하지 않음 |
| source_documents | source_kind, source_url?, external_id?, captured_at?, content_text?, content_hash, source_metadata JSONB | 원문 댓글·설명 등 승인에 사용한 근거. 해시·수집 시점 보존 |
| archive_sources | archive_id, document_id, role(setlist_evidence/metadata_evidence) | 댓글이 여러 개여도 덮어쓰지 않고 근거 연결 |
| performances | archive_id, ordinal, song_id?, start_seconds, end_seconds?, raw_title, raw_artist?, raw_timestamp?, source_document_id? | 방송 안 순번 UNIQUE. 같은 곡 반복 허용. 원문은 곡 매칭 후에도 보존 |
| performance_artists | performance_id, artist_id, role(lead/guest), position | 인원 제한 없는 가창자 연결, 같은 가창 기록/아티스트 중복 금지 |

가창자가 확실하면 host를 폼 기본값으로 제안할 수 있지만 최종 승인에서 확인한다. 알 수 없는 가창자를 임의로 채널 소유자로 확정하지 않는다. 확인된 가창자는 해당 방송의 참여자에도 연결하며 역할은 검수에서 정한다. 가창 관계가 없는 기록도 검수된 미상 상태로 보존할 수 있고 특정 아티스트 통계에서는 제외한다.

곡 미매칭(song_id NULL)은 허용한다. 원문 표기와 시점은 보여주되 임의의 정규 곡을 생성하지 않는다. start_seconds >= 0, end > start, 알려진 영상 길이와의 관계를 확인한다. 같은 시각 시작은 무조건 UNIQUE로 막지 않고 후보 경고로 처리한다. 메들리는 곡이 바뀌는 구간별 행, 출처가 불명확하면 구간을 임의로 쪼개지 않고 보류한다.

top_comment 한 칸 대신 근거 문서를 연결한다. timestamp_text는 시점 숫자에서 화면용으로 계산하고 실제 원본 문자열만 raw_timestamp에 남긴다. 영상의 비공개/삭제와 세트리스트 완성 상태를 하나의 status에 섞지 않는다.

짧은 영상이라는 이유만으로 420초 이하를 새 DB의 모든 조회에서 숨기지 않는다. 검수에서 라이브/커버/기타 분류를 확정하고 승인된 live_archives만 대상으로 삼는다.

### D. 공연

| 테이블 | 주요 필드 | 관계·규칙 |
| --- | --- | --- |
| concerts | title, event_format, event_date?, starts_at?, ends_at?, timezone_name?, time_precision(unknown/date/datetime), city?, venue?, status(scheduled/postponed/cancelled/completed), source_document_id? | 날짜만 아는 공연을 가짜 자정으로 저장하지 않음 |
| concert_artists | concert_id, artist_id, position | 역할 구분 없이 출연진과 표시 순서만 관리. 첫 출연자를 대표 이름·색상으로 사용 |
| concert_ticket_windows | concert_id, label?, opens_at?, closes_at?, url?, price_text? | 선행/일반/추첨 등 여러 판매 구간. 자동 응모 없음 |

날짜만 알려졌다면 event_date와 date 정밀도를 사용한다. 시각까지 알려졌다면 TIMESTAMPTZ와 IANA 시간대(예: Asia/Tokyo)를 기록한다. 날짜 불명도 저장할 수 있으나 캘린더에는 표시하지 않는다. 정밀도와 값의 일관성을 검증하며 티켓 안내 게시글을 별개 공연으로 자동 추가하지 않는다.

온라인 공연은 DB에 저장 가능하지만 현재 사용자 캘린더는 onsite/hybrid만 표시한다. 공동 공연은 공연 한 건으로 저장하고 여러 출연자로 연결한다. 즐겨찾기 필터에서도 같은 공연 카드를 중복 생성하지 않는다.

### F. 출처·변경·안전한 반영

| 테이블 | 목적 |
| --- | --- |
| catalog_instance | 이 DB 카탈로그의 UUID·스키마 식별. 대상 착오 및 프론트 저장키 혼동 방지 |
| catalog_imports | operation_id UNIQUE, manifest_hash, committed_at, 결과 ID 매핑. 원격 저장 영수증 |
| catalog_changes | 작업 ID, 대상 타입/ID, 변경 전후 또는 변경 필드, 적용 시각 |

기존 DB의 table/id와 새 ID 대응은 저장하지 않는다. 새 초안의 client_ref와 새 DB ID 대응은 반영 확인·재시도용으로만 유지한다. 핵심 음악 관계는 일반 FK로 관리한다.

검토 상태/AI 후보/로컬 메모를 위 테이블에 복제하지 않는다. 수동 저장도 operation_id와 변경 이력을 남겨 재시도·실수 복구의 근거로 사용한다. 되돌리기는 과거 값으로의 새로운 검수된 변경이며 이후 수정 내용을 무시한 자동 rollback이 아니다.

## 7. 통계 기준 제안

현재 프론트와 향후 곡 상세에서 같은 기준을 사용한다.

- 가창 1회 = performances 한 행. 두 사람이 함께 불러도 곡의 총 가창 추이는 한 번이다.
- 특정 아티스트의 횟수 = 그 아티스트가 performance_artists에 연결된 가창 행 수. 듀엣이면 두 가창자의 개인 횟수에는 각각 1회다. 그룹 전체를 멤버 전원으로 자동 확장하지 않는다.
- 아티스트 활동량/방송 개수 = archive_artists에 참여로 연결된 DISTINCT archive. 방송만 참여하고 가창이 없어도 방송 수에는 포함한다. ‘진행 방송만’이 필요하면 role=host로 별도 제공한다.
- 곡 종류 = DISTINCT song_id. 미매칭 곡은 종류 수에서 빼고 미매칭 가창 수를 별도로 제공한다. raw_title마다 정규 곡 수를 늘리지 않는다.
- 아티스트 순위는 song_artists에 연결한 원곡 명의로 집계한다. 공동 원곡자 n명은 원곡자별 포함 횟수에는 각각 1회, 비율은 해당 가창의 1/n씩 배분하는 안을 권장한다. n은 서로 다른 아티스트 ID 수이며 동일 연결을 중복 계산하지 않는다. 포함 횟수와 비율의 의미가 다르므로 API 필드를 구별하고 안내한다.
- 대안은 참여 횟수/총가창 비율이며 이때 공동 원곡 때문에 비율 합이 100%를 넘을 수 있다. 구현 전 최종 표시 정책을 사용자와 확인한다.
- 원곡자 미확정 가창은 비율 분모의 미확정 몫으로 유지한다. 알려진 원곡자만으로 100%를 다시 맞추지 않는다.
- 월은 실제 방송 시각을 Asia/Seoul로 환산한다. 방송 시각 미정인 업로드는 날짜 미정 가창으로 남기며 업로드 월을 실제 가창 월로 조용히 대체하지 않는다. 화면에는 공개일 fallback을 별도 표시할 수 있다.
- 커버 업로드·발매 녹음은 라이브 가창 통계에 자동 포함하지 않는다. 향후 필요하면 자료 종류별 필터로 구분한다.
- 미래/날짜 미정 방송은 과거 활동량 그래프에서 제외한다. 정렬 동률과 페이지 순서는 ID까지 포함해 안정적으로 만든다.

월별 곡 추세는 song_id+방송 월, 많이 부른 아티스트는 song_id+performance_artists.artist_id로 조회 가능하다. 추세는 절대 횟수와 수집된 전체 가창 대비 비율을 구분한다.

## 8. 조회 성능과 제약

기존 96회 아티스트 반복 조회를 새 모델에 다시 만들지 않는다. 초기에는 일반 SQL 집계와 인덱스로 시작하고 실제 계측 후 필요한 캐시·집계표만 추가한다.

필수 후보 인덱스: performances(archive_id, ordinal), performances(song_id, archive_id), performance_artists(artist_id, performance_id), archive_artists(artist_id, archive_id), live_archives(broadcast_at, id), song_artists(artist_id, song_id), concert_artists(artist_id, concert_id), concerts(event_date, id), album_tracks(album_id, disc_number, track_number). UNIQUE가 만드는 인덱스를 중복 추가하지 않는다.

검색은 이름/별칭과 곡명 정규화 키부터 시작하며 substring 검색 규모를 측정해 pg_trgm GIN을 선택한다. pg_trgm 설치를 현재 완료로 가정하지 않는다. 통계는 곡/아티스트별 검색·정렬·10행 페이지를 서버에서 제공하여 기존 “모든 집계 행을 한 번에 반환”하는 한계도 해소한다. 외부 API·LLM은 읽기 요청에서 호출하지 않는다.

배포/스키마 마이그레이션은 직접 연결, 실행 중 조회·관리 요청은 풀 연결을 분리할 수 있다. 현재 SQLAlchemy 공유 풀을 유지하고 Neon pooler와의 동작을 검증한다. [Neon 연결 풀 안내](https://neon.com/docs/connect/connection-pooling)

## 9. 기존 코드와 새 카탈로그의 실행 경계

**.env의 DATABASE_URL을 새 DB 주소로 교체하지 않는다.** 기존 `read_catalog.py`와 구형 관리 API·초기화는 기존 스키마에 의존한다. 2026-09-20 사용자 `/api/v2`는 별도 `catalog_read.py` 서비스·repository와 READ ONLY Session으로 새 DB에 연결했다. 현재 HTTP 계약은 [조회 API v2](read-api-v2.md)를 따른다.

1. 기존 API·수집기·Discord 봇은 `.env`의 `DATABASE_URL`을 유지한다. 새 관리자·마이그레이션·v2 조회는 `.env.catalog`의 `NEW_CATALOG_DATABASE_URL`을 사용한다.
2. 새 migration과 관리자 진입점은 구형 `init_db()`와 시드를 실행하지 않는다. API의 `DATABASE_AUTO_INIT` 기본값은 false다.
3. 초기 데이터는 로컬에서 검수한 뒤 고정 manifest로 명시적으로 반영한다. 데이터 정제·검수와 운영 수집기 이전은 남은 작업이다.
4. 새 repository와 DTO는 복수 가창자·공연 출연진을 관계로 조회한다. 앨범·가사는 저장된 새 카탈로그만 읽고 GET에서 재수집하지 않는다.
5. 새 카탈로그용 즐겨찾기 저장 키를 분리했다. 이전 즐겨찾기를 자동 승계하지 않는다. `catalog_instance` UUID를 이용한 더 세밀한 전환 정책은 현재 구현과 구분해 검토한다.
6. 검증·후속 확장 범위는 [QA](../web/docs/qa.md)와 [백엔드 후속 작업](backend-roadmap.md)에 유지한다. 두 DB의 변경은 URL 교체만으로 합쳐지지 않는다.

기존 dump의 계정 토큰·Discord 소유권·알림 route·last_seen·재시도 카운터는 이 단계에서 새 음악 카탈로그로 옮기지 않는다. 앞으로 수집기를 연결할 때도 후보는 관리자 검수 큐로 보내며 기존 초기 검수 요구를 우회하지 않는다.

## 10. 다음 구현 전에 확정할 항목

통합 명부와 음악 카탈로그 우선 범위는 확정했다. 그 외 표 구조와 검수 관문은 권장 설계안이다.

- 공동 원곡자의 순위 비율: 1/n 기여도 배분 또는 중복 포함 비율.
