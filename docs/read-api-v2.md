# 조회 API v2와 성능 개선

[문서 안내](../README.md) · [구조·운영](backend-architecture.md) · [후속 작업](backend-roadmap.md)

2026-09-18. 새 프론트는 `/api/v2` 조회 API를 사용한다. 기존 API·수집기·DB 테이블과 기존 데이터는 유지한다. 데이터 정제, 중복 삭제, 재수집, DB 인덱스/스키마 변경은 이번 범위에 포함하지 않았다.

## 적용

백엔드는 루트에서 실행한다. --reload가 변경을 반영한 상태에서는 프론트를 새로고침하면 된다. 새 경로가 404이면 오래된 API 프로세스를 재시작한다.

```powershell
.\.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload
```

새 API가 등록됐는지는 `/docs`의 `frontend-read` 그룹으로 확인한다. 이미 실행 중인 오래된 프로세스는 `/health`에 성공하더라도 `/api/v2/artists`에 404를 반환할 수 있다.

프론트는 `front-design-draft`에서 `npm run dev`로 실행한다. `BACKEND_URL` 기본값은 `http://127.0.0.1:8000`이다. 개발 프록시 외의 운영 환경에도 `/api` 라우팅이 필요하다. 검증용 8001/5198 포트는 일반 실행 기본값이 아니다.

## 계약

인증은 기존 선택적 `X-API-Key` 정책을 유지한다. 새 GET에는 수집·번역·데이터 보완 쓰기가 없다. 목록에만 필요한 필드를 반환하고 원문 게시글, 댓글 전체, 중복 setlist JSON, 소유자/토큰 등은 포함하지 않는다.

페이지 응답은 `{ items, total, offset, limit }`이다. offset은 0부터, limit은 1~100, 기본 검색은 50개이다. 잘못된 범위는 422, 없는 리소스는 404. 끝을 넘긴 페이지도 total을 정확히 반환한다. 정렬에는 ID를 마지막 기준으로 사용한다. 데이터가 변경되는 중의 offset 페이지는 동일 시점 스냅샷을 보장하지 않으며 향후 대규모 수집에서는 cursor를 검토한다.

| 경로 (`/api/v2` 아래) | 응답/조건 | 프론트 사용 |
| --- | --- | --- |
| `GET /artists` | 그룹화된 프로필 목록, 원어 name·기존 display_name·별칭·관련 ID·이미지·활성 소스 | 홈·탐색. 데이터 크기가 작은 카탈로그 전체 반환. 대표 영상 조회 없음 |
| `GET /artists/{id}` | 대표 또는 관련 ID로 프로필 조회 | 개별 프로필 대체 조회 |
| `GET /artists/{id}/lives` | 페이지 요약. 최신 방송/공개일 내림차순, ID 내림차순. 세트리스트 없음 | 처음 6개, 더 보기마다 6개. 전체 아카이브를 먼저 내려받지 않음 |
| `GET /lives/{id}` | 저장된 영상 메타데이터와 세트리스트. 시점·ID 순 | 뷰어. 기존 상세 GET의 번역·저장 절차 우회 |
| `GET /artists/{id}/statistics` | 전체 아카이브 수, 가창 수, 곡/원곡자별 집계, 월별 아카이브 수 | 통계 탭에서만 조회. 아카이브 원문 대신 집계 행 전송 |
| `GET /search?q=...` | 곡명/한국어 곡명/원곡자/한국어 원곡자 OR 검색. 날짜 내림차순·시점·ID 순 | 50개씩 더 보기. 기존 두 조건 검색·중복 병합 제거 |
| `GET /concerts` | ready/synced + live_event + onsite/hybrid + 아티스트·ISO 형태 날짜. artist_id/start/end 선택 | 캘린더는 전월~다음달 3개월, 프로필은 대상 아티스트. 100개씩 필요한 범위 끝까지 조회 |
| `GET /concerts/{id}` | 같은 공개 조건을 만족하는 공연 1개 | 팝업이 전체 공연 목록을 재조회하지 않음 |
| `GET /spotify/artists/{id}/discography` | 그룹 관련 ID 중 연결된 Spotify 아티스트의 앨범 요약. 미연결 409 | 오리곡 탭 |
| `GET /spotify/albums/{id}` | 외부 앨범/트랙 + 이미 저장된 한국어 번역 | 앨범 선택 시 조회. 번역 LLM 호출 없음 |

저장된 가사와 Spotify 트랙→song ID 매핑은 기존 읽기 API를 계속 사용한다. 생일, 한국어 아티스트 전용 이름, 공통 곡 ID 생성은 여전히 미지원이며 임의 생성하지 않는다.

### 통계 기준

- 기존과 동일하게 길이 420초 이하 영상은 제외한다. 길이가 미등록된 영상은 포함한다.
- source로 연결된 아티스트 ID를 우선한다. source 없는 영상은 등록된 이름/별칭의 유일한 정확 일치로 연결한다. 부분 일치로 다른 가창자를 섞지 않는다.
- 가창 횟수는 저장된 performance 행 수다. 기존 잘못된/중복 행을 임의 삭제하거나 하나로 합치지 않는다.
- 곡 구분은 NFKC·소문자·공백 정리한 원어 곡명 + 원곡자다. 구두점은 보존한다. 향후 공통 곡 ID로 대체할 수 있다.
- 곡 순위는 횟수 내림차순, 동률 공동 순위(1, 1, 3). 프론트의 네 가지 정렬·곡/아티스트 검색·10행 페이지는 집계 행을 대상으로 수행한다. 이번 단계에서는 고유 곡/원곡자 집계 전체를 한 번 가져오며 서버에서 통계 페이지를 나누지는 않는다.
- 최근 부른 날은 방송일, 없으면 공개일. 없는 날짜는 미정이다. 원곡자 미등록 가창도 전체 횟수 분모에는 포함하되 아티스트 순위에서는 제외한다.
- 활동량은 한국/일본 시간 월 기준, 세트리스트 없는 방송도 포함하며 미래/날짜 미정 방송은 그래프에서 제외한다. 6M/1Y는 현재 월 포함, All은 최초 월~현재 월, 빈 달은 0으로 표시한다.
- 검색 화면의 가창자/원곡자 드롭다운은 현재 불러온 검색 결과에 대한 필터다. 아직 로드하지 않은 페이지 전체의 필터 후보 API는 이번 범위에 없다.
- 공연 start는 포함, end는 제외. 기존 starts_at이 자유 문자열이어서 범위 조회는 명시된 ISO 날짜 부분을 사용한다. offset 없는 시각을 확정 시간으로 해석하지 않는다. DB 시간대 계약 보완은 별도 작업이다.

## 성능 변경

- 새 아티스트 목록은 목록 1회 + 소스 1회로 끝낸다. 아티스트마다 대표 YouTube 영상을 조회하던 반복 작업을 수행하지 않는다.
- SQLAlchemy Engine/연결 풀을 재사용한다. URL별로 구분해 테스트 DB나 설정 변경 시 다른 DB 연결을 재사용하지 않는다.
- 라이브/검색/공연은 페이지 조회와 최소 필드 응답. 통계는 DB에서 고유 곡 단위로 집계한다.
- 프론트의 동시 동일 요청을 합치고 성공 결과를 30초간 재사용한다. 오류는 캐시하지 않으며, 한 화면의 요청 취소가 다른 화면의 요청을 취소하지 않는다.
- Spotify는 성공 응답만 최대 128개/5분 캐시하고 같은 외부 요청을 합친다. 최초 Spotify 요청은 외부 서비스 속도의 영향을 받는다. 캐시된 정보는 최대 5분 늦게 갱신될 수 있다.
- 새 응답의 `Server-Timing`에 DB 처리 시간과 쿼리 수를 기록한다. DB 시간은 SQL 실행·결과 읽기와 첫 연결 획득을 포함하며, 순수 DB 엔진 실행 시간만 의미하지 않는다.

## 측정과 재현

동일 PC/기존 Neon 데이터에 대해 순차 HTTP 요청으로 비교했다. 기존 서버 8000과 변경 코드의 검증 서버 8001을 사용했다. 작은 표본이므로 네트워크·DB 활성 상태·연결 풀의 온도에 따라 달라진다. 브라우저 이미지 다운로드와 렌더링 시간은 포함하지 않는다.

| 요청 | 기존 | 변경 후 | 응답 크기 |
| --- | --- | --- | --- |
| 아티스트 목록 첫 요청 | 9.93초 | 1.47초 | 59,959 → 26,602 bytes |
| 아티스트 목록 반복 | 8.00초 | 0.39초 | 변경 후 DB 쿼리 2회 |
| 라이브 목록 초기 표시 | 전체 1.16초 | 첫 6개 0.49초 | 1,521,022 → 2,169 bytes |
| 통계 | 위 전체 아카이브를 프론트에서 계산 | 집계 응답 0.87초 | 321,454 bytes, 탭 선택 시만 요청 |
| 검색 | 곡명 0.87초 / 원곡자 0.70초 (병렬) | OR 검색 첫 50개 0.36초 | 기존 합 114,351 → 21,945 bytes |
| 공연 | ready 목록 0.65초 | 선별 목록 첫 100개 0.30초 | 936,104 → 52,792 bytes |

목록 비교는 초기 표시까지 필요한 작업을 비교한 것으로, 전체 목록 전송 완료 시간 비교가 아니다. 기존 검색 두 요청은 병렬이므로 소요 시간을 단순 합산하지 않는다. 실제 달력은 월 범위 조건을 추가하므로 표의 전체 첫 페이지와 다를 수 있다.

원시 측정값은 [변경 전](../front-design-draft/docs/performance-before.json), [변경 후](../front-design-draft/docs/performance-after.json), [SQL 프로파일](../front-design-draft/docs/performance-queries.json)이다. 재측정은 루트 가상환경 Python으로 `front-design-draft/scripts/benchmark-api.py before|after`를 실행한다. `BENCHMARK_API_URL`로 주소를 바꿀 수 있다. `profile-catalog.py`는 명시적인 읽기 전용 트랜잭션에서 SQL 횟수/시간만 측정하며 레코드·인증정보를 출력하지 않는다.

실제 SQL 프로파일에서 기존 목록은 94개 등록 아티스트의 대표 영상 조회를 94번 추가 실행했다. 총 96개 쿼리, 서비스 처리 약 7.47초 중 대표 영상 조회가 7.17초였다. 새 목록은 같은 75개 그룹을 2개 쿼리로 반환했고 같은 연결 조건에서 서비스 처리 약 0.17초였다. 이는 HTTP 전체 시간과는 다른 측정이다.

## 남은 범위

기존 서비스가 유지되고 있어 `/api`의 기존 경로를 삭제하지 않았다. 과거 코드의 psycopg 직접 연결·관리 작업은 유지된다. 기존 데이터 오염 정리, 공통 곡 ID, 계정 권한 개편, 대규모 통계 페이지 API, DB 인덱스 변경은 별도 단계다.
