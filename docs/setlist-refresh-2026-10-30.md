후속: API 키 저장·크레딧 충전 후 수행한 [2026-10-31 모델 복구](setlist-model-recovery-2026-10-31.md)에서 모델 보류 1,165개를 모두 재처리했다. 아래 인증 오류와 수치는 2026-10-30 당시 기록이다.

사용자 요청으로 신규 통합 DB의 활성 라이브 중 활성 가창 기록이 없는 항목을 조사하고 재수집했다. 기존 DB는 접근하지 않았다. 최초 빈 라이브는 1,756개이며 활성 YouTube 계정과 연결된 대상은 1,755개다. 계정 미연결 1개는 `GRMtBaDEEYE`로, 기존 제목이 `Dusk / HACHI … Official MV …`인 항목이다. 이름만으로 계정을 연결하거나 라이브를 삭제하지 않았다.

## 원인과 실행 범위

웹의 `준비중`은 실제 작업 상태와 무관하게 `performance_count`가 없거나 0이면 표시된다. 조사 당시 빈 라이브의 최신 원문 기록은 모델 일시 오류 860개, 응답 검증 실패 395개, 댓글 대기 종료 392개, 댓글 대기 13개, 댓글 비활성화 7개, 판단 보류 1개, 나머지 기타/기존 자료 88개였다. 이는 최신 원문 이력의 분류이며 새 수집 결과와 구분한다.

갱신한 DB 접속 정보는 정상 인증됐다. YouTube API도 정상이나 설정된 모델 API는 실호출에서 HTTP 401 `invalid_api_key` 오류를 반환했다. 이는 이번 요청의 인증 실패이며, 잔액·사용량 소진 여부를 확인한 결과는 아니다. 따라서 이번 임시 실행에서만 모델 호출을 비활성화하고, 저장 원문 또는 최신 댓글을 현재 규칙으로 검증해 확정 가능한 곡만 반영했다. `.env`와 정상 worker의 활성화 설정은 변경하지 않았다.

`refresh-empty-2026-10-30` 요청의 typed payload·멱등 key로 작업을 기록했다. 임시 일괄 실행은 이 요청의 정확한 작업 ID만 lease로 선점하고 두 실행에서 각각 최대 5개, 합계 최대 10개를 병행했다. 실행별 HTTP 시작 간격은 최소 0.15초이며 기존 adapter의 기본 1초 간격도 유지했다. provider quota/Retry-After에 따른 중단을 유지했다. 일반 worker의 provider당 작업 1개 제한과 구분되는 일회성 실행이다. 저장에는 기존 계정 검증·lease 확인·snapshot 충돌 검사·원자 저장을 사용했다. 기존 곡 목록을 덮어쓰거나 원문을 삭제하지 않았다. Discord·Calendar·Spotify·가사·번역 수집은 실행하지 않았다.

## 코드 보완

- `worker_jobs.claim`: 작업 후보마다 provider 작업 이력을 재검색하던 상관 subquery를 provider당 한 번 검사하도록 바꿨다. 대량 대기열에서 실제 조회 시간 제한이 발생해 확인한 변경이다. advisory lock·실행 중 검사·최소 간격·quota 보류와 만료 lease 정리를 유지한다.
- `persist_collect`: 보관된 가창 기록이 있는 라이브는 빈 신규 항목으로 취급하지 않는다. 기존 `archive_id, ordinal` 고유 제약 충돌을 방지하고, 사람이 제거한 목록을 재생성하는 대신 원문 후보만 보존한다.

코드 보완은 로컬 변경이며 운영 배포·API 재시작은 수행하지 않았다. 이번 요청의 신규 DB 자료 갱신과 코드 배포 상태는 구분한다.
