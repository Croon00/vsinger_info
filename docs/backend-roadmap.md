# 백엔드 후속 작업

기준: 2026-09-19. 현재 계약은 [조회 API v2](read-api-v2.md), 실행 구조는 [백엔드 구조](backend-architecture.md), 완료 검증은 [QA](../web/docs/qa.md)에 있다. 이 문서는 남은 작업과 아직 새 프론트에서 사용하지 않는 기능을 관리한다.

아티스트·라이브·검색·서버 집계 통계·공연·Spotify 조회는 연결되어 있다. v2 추가와 연결 풀 재사용은 완료했고, 당시 DB 스키마·데이터는 변경하지 않았다. 미지원 데이터는 실제 화면에서 목업으로 보충하지 않는다.

## 현재 백엔드로 제공할 수 없는 기능

| 우선순위 | 작업                                 | 현재 제한                                                                                           | 이번 프론트 처리 / 완료 조건                                                                                                                                                                      |
| -------- | ------------------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1       | 아티스트·그룹 멤버 생일              | Artist 응답에 생일·멤버 계약 없음                                                                   | 실제 모드에서 생일 필터와 생일 생성 제거. 월·일 저장 및 멤버 소속 API를 추가하면 연결한다.                                                                                                        |
| P1       | 원어/한국어/기타 별칭 이름 분리      | `name`, `display_name`, `name_aliases`는 존재하나 언어 의미가 보장되지 않음                         | 기존 `name` 표시, `display_name`과 별칭은 검색에만 사용. 임의 한국어 표기 생성 안 함. `name_native`, `name_ko`, aliases 계약과 데이터 정리 필요. 곡·원곡 아티스트의 `_ko`는 기존 응답을 사용한다. |
| P1 | 라이브의 영구 artist ID 연결 | v2는 source ID를 우선하고 source 없는 행은 유일한 이름/별칭으로 연결 | 이름 기반 기존 행에 영구 가창자 관계를 저장하는 작업은 향후 정제 단계에 필요. |
| P1       | 공개 읽기 인증과 관리자 권한 분리    | 일부 라우터만 선택적 공용 X-API-Key 사용, Spotify는 보호 방식 다름                                  | 개발 프록시의 서버 전용 키만 지원. 공개 배포 전 읽기·쓰기 경계와 사용자 세션 정책 확정 필요. 브라우저 번들에 관리 키를 넣지 않는다.                                                               |
| P2 | 대규모 통계의 서버 페이지·검색·정렬 | v2 서버 집계·월별 활동량은 완료. 고유 곡/원곡자 집계 전체를 반환 | 현재 10행 페이지와 정렬·필터는 작은 집계 응답에서 처리. 데이터 증가 시 통계 API 자체 페이지 추가. |
| P2       | 공연의 도시·정확한 시간대·확정 상태  | 도시 없음, starts_at은 자유 문자열; UTC offset 없는 값 가능                                         | 도시 생략. 서버가 시간대 포함 ISO 날짜를 저장하도록 계약 명확화 필요. 현재 날짜만 있거나 offset 없는 일정은 날짜만 표시하고 시간 미정 처리.                                                       |
| P2       | 독립 프로필 이미지·출처·크롭         | 현재 Spotify 이미지 URL만 제공                                                                      | 기존 URL 또는 이름 폴백 사용. 공식 프로필 자산 관리가 필요하면 전용 필드 추가.                                                                                                                    |
| P2 | 기존 서비스의 읽기 부작용 정리 | 새 프론트의 v2는 번역/정보 보완 쓰기를 하지 않음. 기존 API 동작은 유지 | 기존 서비스 폐기/이전 이후 과거 상세 조회와 수집 절차 정리. |

## 실행·검증 후속 작업

- [ ] 실제 DB의 이름·별칭 중복, 라이브 연결 누락, 이미지 URL, 공연 시간대 점검.
- [ ] Spotify 미매칭 아티스트를 기존 관리 기능으로 연결할지 운영자가 결정. 프론트가 자동 동기화·생성 요청을 보내지 않는다.
- [ ] Spotify 최초 외부 요청의 실제 지연 추가 측정. 새 상세 조회는 번역을 분리했고 Spotify 캐시·실패 처리는 fixture로 검증했다.
- [ ] 운영 동일 출처 `/api` 라우팅과 권한 검증. 로컬 Vite 프록시는 배포 서버 구성을 대신하지 않는다.


## 데이터 품질과 운영 경로

- [ ] [새 DB 구조·이전 계획](db-renewal-plan.md)을 구현한다. 별도로 준비된 빈 Neon DB의 읽기 전용 연결을 확인했으며 통합 아티스트 명부·음악 카탈로그 우선 이전은 사용자 결정으로 확정했다. 현재 실행 앱은 기존 DB를 사용한다.
- [ ] [관리자 로컬 웹 계획](admin-web-plan.md)에 따라 JSON 후보·원본 댓글·영상·차이를 검수하는 도구를 구현한다. 초기 반영 대상은 사용자가 전부 검수한 뒤 명시적으로 저장한다. 기존 ready 상태나 LLM 결과를 자동 승인하지 않는다.
- [ ] 오염된 곡·중복 영상·미확정 가창자 연결을 실제로 검수한다. 덤프 집계와 조회 최적화가 데이터를 정제한 것은 아니다. 재수집/로컬 LLM 실행은 별도 작업이며 원문·외부 ID·출처·생성 버전을 보존한다.
- [ ] X 분류→공연 추출→Calendar 자동화가 다시 필요하면 현재 notice 알림 경로와 통합 방법을 정하고 별도 검증한다. music_graph.py와 Calendar helper는 존재하지만 scheduler에 자동 연결된 상태는 아니다.
- [ ] 기존 서비스 사용 종료가 확인되면 중복 API·호환 경로·레거시 읽기 부작용을 단계적으로 제거한다.

## 구현되어 있으나 현재 화면에서 사용하지 않는 API

| API 또는 기능                                             | 미사용 이유 / 활용 위치                                                 |
| --------------------------------------------------------- | ----------------------------------------------------------------------- |
| `GET /api/youtube-performance-stats`                      | 전체 상위 200개 집계이며 현재 아티스트별 통계와 기준이 다름.            |
| `GET /api/youtube-covers`                                 | 커버 업로드 화면을 추가할 때 활용. artist_id/collaborator_id 필터 있음. |
| `GET /api/youtube-performance-filters`                    | 다중 조건 검색 UI의 후보 목록. 현재는 자유어 검색.                      |
| `GET /api/artist-agencies`                                | 현재는 조회된 아티스트의 소속사만 필터에 사용.                          |
| 아티스트·소속사·소스 POST/PATCH/DELETE                    | 관리자 등록/수정 UI.                                                    |
| `POST /api/event-candidates`                              | 관리자 공연 후보 등록.                                                  |
| `POST /api/youtube-lives`, `/api/youtube-lives/backfills` | 영상 등록·과거 수집. backfill은 202 응답, 작업 진행 조회 계약 없음.     |
| `PATCH /api/youtube-performances/{id}`                    | 세트리스트 메타데이터 교정. 타임스탬프 수정은 현재 요청 모델 미지원.    |
| Spotify 아티스트 목록·후보·프로필 조회                    | 등록·매칭 관리.                                                         |
| Spotify sync·youtube-auto-link·enable·exclude             | 관리자 데이터 준비·노출 설정. 페이지 방문으로 실행하지 않음.            |
| `GET /api/spotify/relationships`                          | 공동 발매 관계 화면.                                                    |
| songs/from-youtube·spotify-track-youtube·credits 변경     | 가사 생성·곡 연결·크레딧 관리.                                          |
| Google auth/start·callback                                | Google Calendar 계정 연동. 웹 사용자 로그인 기능과 다름.                |

Discord 라우팅·수집 worker·Google Calendar 동기화는 새 프론트 네 메뉴의 직접 HTTP 소비 범위 밖이다. 내부 기능이 존재하는 것을 웹용 HTTP API 제공으로 간주하지 않았다.


## 향후 버전: 곡을 기준으로 탐색·통계 (사용자 요청)

현재 버전의 화면 구현 범위에는 포함하지 않는다. 새 구조의 상세 기준은 [DB 구조 계획](db-renewal-plan.md)에 모으고 아래에는 남은 화면·조회 작업을 둔다.

- 목표: 곡 목록 및 상세, 해당 곡을 많이 부른 아티스트, 월별 가창 추이, 곡 정보.
- 기존 songs는 YouTube/Spotify/가사 중심이며, youtube_song_performances에는 이를 참조하는 song_id가 없다. 제목 문자열만으로 동일 곡을 집계하지 않는다.
- 확정된 통합 명부와 계획된 곡/녹음 분리 구조를 구현한다. 원곡자·합동 가창은 역할별 다중 관계로 연결하며 탐색 노출 여부와 독립적으로 등록한다.
- 미매칭 가창의 nullable song_id와 원문 보존, 기존 ID 매핑은 DB 계획에 따른다. 원어/한국어/영문 필드로 곡을 검색하고 곡 별칭은 후속 확장으로 남긴다.
- 기존 가사 song_id 참조를 깨뜨리지 않도록 확장 또는 별도 canonical 곡 테이블 연결 후 이전한다. 기존 데이터 일괄 덮어쓰기/제목만으로 자동 병합하지 않는다.
- 집계 기준: 한 번의 가창을 기본 단위로 정의하고, 메들리·반복·부분 가창·합동 가창·재업로드 처리 및 버전 합산 기준을 명시한다.
- 월별 추이는 가창 횟수와 별개로 전체 수집 가창 대비 비율을 제공할지 검토한다. 수집량 증가를 곡 인기 상승으로 오인하지 않도록 기준을 설명한다.
- 현재 단계에서는 관계와 이전 경로만 준비한다. 곡 상세 UI·완성된 통계 API·별도 검색 시스템은 이후 범위다.
