# 검증 가이드와 결과

## 2026-09-24 모바일 캘린더 리스트 스와이프 영역

모바일 리스트 보기에서 일정이 적거나 없어도 기존 달력 격자가 차지하던 높이까지 스와이프 영역을 유지한다. 목업 모바일 브라우저 테스트에서 빈 리스트의 아래쪽 공간을 스와이프해 다음 달로 이동하고 이전 달로 복귀하는 동작, 리스트 높이와 기존 달력 높이, 기존 일정 선택을 확인했다. 관련 PC·모바일 브라우저 테스트 4개와 TypeScript 검사·프로덕션 빌드가 통과했다.

## 2026-09-24 캘린더 월 버튼 전환

PC·모바일의 이전/다음 달 버튼에 방향별 달력 전환을 적용하고, 전환 중 중복 클릭을 막았다. 모션 감소 설정에서는 애니메이션 없이 월을 바꾼다. 목업 브라우저 테스트 PC·모바일 각 2개에서 양방향 애니메이션 프레임, 월 이동, 기존 모바일 스와이프, 모션 감소 동작을 확인했다. TypeScript 검사와 프로덕션 빌드가 통과했다.

## 2026-09-24 모바일 캘린더 월 이동 버튼

모바일 월 제목 양옆에 ghost 이전/다음 달 버튼을 추가했다. 목업 PC·모바일 브라우저 테스트 각 1개에서 모바일 버튼의 좌우 배치, 다음 달 이동·이전 달 복귀, 기존 스와이프 동작을 확인했다. TypeScript 검사와 실제 모드 빌드가 통과했다.

## 2026-09-24 캘린더 아티스트 색상·인접 월 일정

격자에 보이는 앞뒤 달 일정과 연도 경계의 생일을 표시하고, 다른 달의 일정은 낮은 투명도로 구분했다. 일정 배지는 유효한 아티스트 theme_color를 카드 배경과 섞어 라이트·다크 모드별 연한 색으로 표시하며 글자는 카드 전경색을 쓴다. 앞뒤 달 일정의 기본 투명도는 0.22다. 실제 모드 HTTP fixture 브라우저 테스트 PC·모바일 각 1개에서 앞뒤 달 일정·모드별 배경색·투명도와 12월 격자의 다음 해 1월 생일을 확인했다. 기존 실제 모드 계약 및 월 이동 테스트 3개, 목업 PC·모바일 캘린더 테스트 2개와 TypeScript 검사·프로덕션 빌드가 통과했다. 실제 DB를 변경하거나 사용하지 않았다.

## 2026-09-24 캘린더 월 이동 로딩

월 이동 중 날짜 격자와 조작 버튼을 유지하고 일정 로딩 문구 없이 이미 받은 월의 일정을 즉시 표시하도록 변경했다. 공연 요청은 표시 중인 달과 앞뒤 한 달씩 총 3개월이며, 받은 공연은 월별로 보관한다. 아티스트 명부의 화면 상태는 월 이동 조회와 분리하고 같은 날짜의 일정은 날짜별로 묶어 렌더링한다. 지연·실패한 다음 달 API 응답을 사용한 실제 모드 HTTP fixture 브라우저 테스트(PC 1개)에서 격자와 기존 일정 유지, 월별 요청 범위, 오류 후 재시도를 확인했다. 기존 실제 모드 계약 테스트 PC·모바일 2개와 목업 캘린더 월 이동·모바일 스와이프 테스트 2개, TypeScript 검사·실제 모드 빌드, 웹 단위 테스트 27개가 통과했다. 실제 DB 응답 시간 측정은 이번 검증에 포함하지 않았다.

## 2026-09-24 통합검색 필터 예외

실 DB 읽기 전용 `하치` 검색의 첫 50건 중 원곡 아티스트 표기가 빈 행 18건을 확인했다. 이 값이 빈 `SelectItem`으로 렌더링되면 Reka Select가 예외를 내며, 필터 메뉴의 입력 잠금이 남아 링크 클릭이 막힐 수 있었다. 빈 원곡자·가창자 이름은 필터 선택지에서 제외하고 결과 행은 유지했다. 실응답을 사용한 로컬 Chrome 재현에서 콘솔 예외 없이 필터를 열고 닫은 뒤 아티스트 링크로 이동했다. 빈 이름 fixture의 PC·모바일 브라우저 테스트 2개와 TypeScript 검사가 통과했다. DB 변경은 수행하지 않았다.

## 2026-09-24 라이브 뷰어 복귀

통합검색의 세트리스트에서 뷰어에 들어간 뒤 곡 이동·새로고침을 거쳐 `뒤로가기`로 검색어가 유지된 결과 페이지에 복귀했다. 뷰어 직접 진입 때 아티스트 라이브 목록으로 이동하는 경로도 확인했다. mock PC·모바일 브라우저 테스트 각 1개가 통과했다.

## 2026-09-23 보완 6단계

실제 모드 웹 단위 테스트 26개, PC·모바일 HTTP fixture 브라우저 테스트 4개, TypeScript 검사·프로덕션 빌드가 통과했다. 신규 DB를 읽는 로컬 브라우저에서 아티스트 70명, HACHI 라이브 266개, 라이브 상세의 YouTube 연결과 가창 9곡, 프로필 이미지 로드를 확인했다. 당시 신규 DB에 앨범·활성 가사 행이 없어 앨범 빈 상태만 실데이터로 확인했고, 앨범·가사 내용/오류 상태는 fixture 테스트로 확인했다. 운영 배포 웹·프록시 검증은 남아 있다. 백엔드 전체 결과와 운영 경계는 [6단계 결과](../../docs/backend-service-step-6-validation.md)에 둔다.

현재 설계는 [화면 설계](design-plan.md), 실제 API와 측정값은 [조회 API v2](../../docs/read-api-v2.md)를 따른다. 과거 단계마다 누적된 테스트 숫자와 폐기된 UI 설명은 제거했다. 아래 결과는 해당 날짜의 기록이며 이후 변경까지 자동 보장하지 않는다.

## 표준 검증

2026-09-19 디렉터리 이동 후 `web`에서 TypeScript 검사·프로덕션 빌드를 통과했다. 새 프론트 추적 파일 400개와 기존 프론트 50개의 이동 대상 존재 여부, 문서 링크와 `git diff --check`를 확인했다. 아래 기능 테스트 결과는 2026-09-18 기록이며 이동 작업에서 다시 실행하지 않았다.

프론트 디렉터리에서 실행한다.

```powershell
npm test
npm run test:e2e
npm run test:integration
npm run build
```

| 검증 | 대상 | 외부 의존 |
| --- | --- | --- |
| npm test | 데이터 변환, 요청 캐시/취소, 검색·날짜·통계 | mock/fixture |
| test:e2e | 목업 PC·모바일, 탐색·검색·팝업·영상 시점·통계·캘린더·테마 | 플레이어는 테스트 더블 |
| test:integration | 실제 API 모드의 v2 응답 변환·화면 연결 | HTTP 응답 fixture, 실제 DB 없음 |
| build | Vue TypeScript 검사 + 실제 모드 Vite 빌드 | 실제 DB 없음 |
| build:mock | 목업 배포 빌드 | 실제 DB 없음 |

Playwright는 설치된 Chrome을 사용하며 다른 경로는 CHROME_PATH로 지정한다. mock 서버는 5195번, integration은 5196번이다. 결과도 test-results/mock, test-results/integration으로 분리한다.

백엔드 관련 회귀 테스트는 루트 가상환경에서 실행한다.

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_read_api.py tests/test_spotify.py tests/test_youtube_service.py tests/test_artist_identity.py -q
```

## 2026-09-18 조회 API v2 검증

- 백엔드 관련 회귀 테스트 30개 통과.
- 프론트 단위 테스트 24개, mock E2E 28개, API 계약 fixture E2E 2개 통과. 마지막 브라우저 테스트 명령은 정상 종료했다.
- TypeScript 검사·실제 모드 프로덕션 빌드·git diff --check 통과.
- 실제 Neon 연결: PC 1440px / 모바일 390px에서 라이브 첫 6개 → 더 보기 12개, 통계 10행, 캘린더를 확인했다. 확인 경로에서 API·런타임 오류와 가로 넘침이 없었다.
- 일반 8000번 API에서도 v2 아티스트 목록 200을 확인했다. 검증용 8001/5198 서버는 종료했다.
- DB 스키마·레코드 변경, Spotify 최초 실제 외부 요청 측정, 공개 배포 검증은 포함하지 않았다. 데이터 품질을 보증하는 검증도 아니다.

문서 정리에서는 프로그램 코드를 변경하지 않았다. 위 결과를 문서 정리 시점의 새로운 테스트 실행으로 간주하지 않는다.

## 수동 점검

홈·탐색·아티스트 네 탭·검색·뷰어·캘린더/리스트·설정·공연/가사 팝업을 PC/모바일 및 라이트/다크에서 확인한다.

- 긴 이름·이미지 실패에서도 카드 폭과 즐겨찾기 위치가 유지되는지.
- 검색어 Enter·뒤로가기·새로고침과 팝업 포커스 복귀가 일관적인지.
- 통계의 마지막 페이지에서도 문서 높이·스크롤·버튼 위치가 움직이지 않는지.
- 캘린더 5주/6주·다른 달·일정 넘침·모바일 스와이프·작은 화면 스크롤·독 여백이 유지되는지.
- 키보드 조작과 모션 감소 환경에서 정보와 기능이 빠지지 않는지.

성능 재측정은 API 문서의 benchmark/profile 도구를 사용한다. scripts/verify-live-read.mjs는 5198번 프론트·실제 아티스트 ID 2를 가정한 당시 환경 전용 도구다. 다른 환경에서는 URL·ID·아카이브 수 전제를 조정해야 한다.

## 과거 디자인·영상 검증 자료

2026-09-15 Luma CLI view 18종과 로컬 UI 135개를 대조했다. [레지스트리 기록](luma-registry-audit.json)은 당시 자료이며 현재 원격 레지스트리와 항상 같다는 의미는 아니다. 프로필 1:1·14px 반경, ToggleGroup 방향, Card 조합, 키보드 동작을 검수했다.

2026-09-16 디자인 점검은 320/390/900/1440px와 라이트·다크에서 수행했다. [screenshots](screenshots/)는 당시 자료다. 캘린더·검색·통계는 이후 변경되었으므로 오래된 캡처를 최신 사양으로 쓰지 않는다.

같은 날 실제 Chrome에서 목업 HACHI #182/#181/#171 영상의 재생 상태 1, 시간 증가와 디코딩 프레임 증가를 확인했다. #171은 1,088초 시작과 587초 세트리스트 이동도 확인했다. 모든 곡을 청취 검수한 결과는 아니다.

현재 뷰어는 자동재생을 요청하고 차단 시 음소거 재생을 시도한다. localhost와 Referrer-Policy를 사용하며 YouTube 헤더 위조·영상 프록시는 하지 않는다. 외부 네트워크·공개 상태·브라우저 정책에 따라 재생 가능 여부가 달라진다. 테스트 더블 성공을 실제 재생 성공으로 간주하지 않는다.

기존 scripts/check-video.mjs, inspect.mjs, design-audit.mjs는 과거 목업 ID·5174번 포트·일부 고정 개수를 전제로 한다. 특히 check-video는 아카이브 3개를 가정하여 확장된 목업과 다르므로 그대로 실행하는 표준 명령으로 안내하지 않는다. 필요한 환경·개수 전제를 수정한 뒤 사용한다. 이번 문서 정리에서는 도구 코드를 변경하지 않았다.
